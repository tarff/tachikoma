# Splitting App.tsx

**Goal:** App.tsx (2,324 lines on main at 5c8dff8) becomes a short file that wires the screen together, with each area
of what it does in a file of its own. Nothing a user sees or types changes.

**Branch:** `split-app`, from main at 5c8dff8. Its own pull request, as agreed before release 6 merged.

## How the file is built today

App is one React function. About 80 `useRef`s and `useState`s (lines 268-447) hold what is on screen, and about 90
functions defined inside App read and change them and call each other: a key goes `onInput` → `route` → `lookUp` →
`onKey` → `promptKey` → `run` → `send` → `submit` → `perform` → `say`. Then the drawing itself (lines 2056-2324).

Each drawing makes all the functions again, and a function keeps the drawing it was made in: a turn that ends calls
the `next()` of the drawing that started it (the comment at `fullNow`, lines 337-340). Only the listeners set up once
reach the latest drawing's functions, through `latest.current` (line 2052): the bus's handlers, `bindAsk`'s question,
the mouse reports, the settings watch and a picture read's end (`newPicture`).

## The approach (recommended)

Every function moves into an area file **as it is**, reading what it read before from two objects, each made again
at every drawing:

- **`ui`**: everything App's functions read that is not a function of an area. Made by `useAppState(props)` in
  `state.ts`, it holds, each under the name App gives it now:
  - every prop, `pictures` under `picturesGiven` as App names it;
  - Ink's `exit` and `suspendTerminal` (`useApp`), and `columns` and `height` (`useWindowSize`);
  - every `useRef` and `useState` of lines 268-447, setters included, plus `notes` and `newEdit` (470-471) and
    `history` (481), with their comments;
  - the values and helpers of that section that read only those: `keyOf`, `pane`, `cycle`, `question`, `rerender`,
    `clearCopied`, `running` (670), `phaseRefs` and `happening` (689-690);
  - `drawn`, an object of this drawing's own, which the drawing fills in once it has worked out `viewHeight` (the
    frame, line 2177), the one value the functions read that comes later in the drawing.
- **`fns`**: every area's functions, put together by App at each drawing, area by area, before anything calls them.

Each area file exports one function, `(ui, fns) => ({ ...its functions })`. A function made at one drawing reads that
drawing's `ui` and calls through that drawing's `fns`, so it keeps its drawing's functions, as now. Neither object is
ever changed once its drawing is done, except `drawn`, filled in during it. `latest.current` is set from `fns` at each
drawing, and only the listeners above call through it, as now: no call that went directly goes through `latest`, and
none that went through `latest` goes directly.

The two names are new: neither `ui` nor `fns` is used anywhere in App.tsx now, and the names on them are App's own,
which share one scope today, so none collides with another, nor with a function's own locals (`const s =` at lines
859, 1597, 1692, 1702, 2008 and 2023, `applyEntry`'s `s: Settings`).

**Why not smaller:** moving out only what reads no state (the constants and helpers, the hint row's choice of text,
the `/tasks` lines) takes about 300 lines out and leaves App near 2,000. The tangled middle stays tangled.

**Why not custom hooks with their own arguments:** each would need a long list of refs and functions passed in, the
same coupling written out by hand in every file, for nothing `ui` and `fns` do not give.

## Rules for the move

1. **Code moves, it does not change.** Each function's body and comments stay as they are, except `ui.` or `fns.` in
   front of what it now reads from them. No renaming, no tidying, no new checks.
2. **One allowance for types.** `fns`'s type is made from the area functions' own types, so the type checker can find
   a function whose return type depends on itself through `fns` (errors TS7022, TS7023, TS7024). Such a function gets
   its return type written out, as it is now inferred, and nothing else changes in it.
3. **Comments that point elsewhere** ("perform, below", "bindAsk, above") name the file once the thing they point to
   is in another one ("perform, queue.ts"). Nothing else in a comment changes.
4. **The hooks.** Every drawing calls the same hooks in the same order, as React needs. `useInput` and `usePaste`
   stay in App.
5. **No test changes.** The 480 App tests in `tests/tui/app.test.tsx` test App through its props only, so they pass
   untouched, and are the proof nothing changed. A test file edited in this branch is a sign something did.

## Steps

One commit per step, each one passing before the next starts.

1. `constants.ts` → verify: type check passes, the 480 App tests pass.
2. `state.ts`, with every function still in App reading from `ui` → verify: the same.
3. `fns`, still in App, every call between functions going through it, and `drawn` → verify: the same.
4. One commit per area file, in this order: `output`, `pictureReads`, `liveEdits`, `mouse`, `promptKeys`,
   `keyRouting`, `handover`, `queue` (the most called-into last) → verify after each: the same.
5. Docs: the release 6 design's "Tidying the screen code first" and the main design get a line saying where App's
   areas now live → verify: the README needs nothing, as nothing a user sees changed.
6. Final check → verify: type check, `npm run build`, the full suite (with the 9 PowerShell and disk files that time
   out together run alone, as for release 6), and `git diff --color-moved` on App.tsx showing the areas as moved
   blocks, not rewritten ones.
7. A short check in the terminal for you: start `tachi`, type and send a prompt, scroll with the wheel, open the
   detail view with Ctrl+O, run `/settings` and close the editor.

**Process:** as for release 6. A builder does the steps, then a spec review and a code review, fixing until both
approve; the code review checks rule 1 against `git diff --color-moved`, and that every call keeps its drawing as
the approach says. Then the pull request, held for your review.
